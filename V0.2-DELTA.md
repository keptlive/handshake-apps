# HANDSHAKE-APPS v0.2 — the delta `.pxls` needs to ship

Written 2026-08-24, from building and deploying `.pxls`, the first app built
against this standard that runs outside the browser itself (it is by the same
author), live at `https://pxls.hns.one/` and at the native name `pxls/`.
Companion to `HANDSHAKE-APPS.md`; this document is **only the changes**, stated
tightly enough to implement against. HANDSHAKE-APPS.md v0.2 incorporates them;
where the two differ, HANDSHAKE-APPS.md is normative.

## 0. The headline

**Three of the five items below are new specification. The rest of what
stops `.pxls` shipping is already specified in §11 and simply not built.** Do
not read this as "the standard is wrong" — read it as "the standard is mostly
right, has two real holes, and has no implementation."

The two holes are **D1** (an app cannot authenticate a user to its own
server) and **D5** (an app cannot be used at its own Handshake name). Both
were found by building and deploying one app; neither is visible from
reading the spec.

| | What | Kind | Blocks `.pxls`? |
|---|---|---|---|
| **D1** | `auth.token` — authenticate to the app's OWN server | **NEW SPEC** | **YES — hard blocker** |
| **D2** | `names.primary` — which name is the user's main one | **NEW SPEC** | No, but it makes sign-in wrong |
| **D3** | "the provider is not proof" — normative note | doc only | No |
| **D4** | `names.request({})` with no tld | clarification | No |
| **D5** | An app cannot be used at its own **Handshake** name | **NEW SPEC** | Blocks HNS-native hosting |
| **M** | The mediator itself (§11 "Must be built") | already spec'd | **YES** |
| **R** | Registry accepts an award voucher | registry, not plugin | Prize redemption only |

## D1. `auth.token` — the hole

### The problem

Every capability in v0.1 mediates **app → registry**: `records.propose`,
`names.claim`, `content.publish`. There is no verb by which an app
authenticates a user to **its own server**.

Any app with server-side state needs that first. `.pxls` has a canvas, a
leaderboard and prize entitlements; it must know which name placed a pixel
before it can score anything. `names.list()` returning `matt.w3` is not
proof of anything to a server — it arrives over the wire from the party it
flatters.

Without this verb the only options are to invent a bespoke login (defeating
the point of the standard) or to trust the client (defeating the point of
having a server). So it is a hard blocker.

### The surface

```ts
auth: {
  // A NIP-98 (kind 27235) Authorization header, signed by the control key
  // of a granted name, bound to one request at the APP'S OWN origin.
  token(opts: {
    url: string,          // absolute; MUST be same-origin with ui.entry
    method: string,       // uppercased by the mediator
    body?: string,        // exact bytes to be sent, or omitted
    name?: string         // which granted name; see the ladder below
  }): Promise<string>     // "Nostr <base64 event>"
}
```

> **CORRECTED 2026-09-13.** This originally read "default = the single grant,
> else `UserDeclined` if ambiguous", and shipping it proved that wrong: a user
> who had granted an app two names, neither of them their main identity,
> pressed *Sign in* and the app was told the user had declined. The rule is now
> a three-rung ladder — sole grant, then the primary if granted, then the name
> **most recently granted to this app** — and only an app with no grant at all
> is refused, with `NotGranted`. HANDSHAKE-APPS.md §5.6 is normative; this
> paragraph exists so nobody implements the superseded sentence.

Declared in the manifest as a capability:

```json
{ "cap": "identity.authenticate", "scope": "any-held-name",
  "reason": "Prove which name is placing a pixel." }
```

`.pxls` ships today against the namespaced extension
`one.hns.auth.nip98` (§4.1 permits `com.example.*` ids). Promote it to
`identity.authenticate` in v0.2 and the extension can be retired.

### Mediator obligations (normative)

1. **Origin check is the whole security property.** REFUSE any `url` whose
   origin is not exactly the installed manifest's `ui.entry` origin. This is
   what stops an app minting a signature aimed at `/api/dns/mutate`. Without
   it this verb is a signing oracle over the user's control key.
2. Sign only with the control key of a name **granted to this app**.
3. `created_at` is the mediator's clock. The event is single-use; never
   cache, pre-sign, or reuse one.
4. Return only the header string. Never the key, never the raw event.
5. Rate limit per app id, as for mutations.

### Consent

**Granted once at install; NOT prompted per call.** It authenticates to the
origin the user is already looking at and writes nothing, anywhere. A prompt
per call would put a dialog in the hot path of a game and teach users to
click through consent — precisely the failure §5.4 exists to prevent.

The install-time consent line should say what it is:

> *pxls will be able to prove you are **matt.w3** to pxls.hns.one. It cannot
> use this to change your names or records.*

### Why NIP-98 and not something new

`signAuth` in `browser/src/identity/identity-account.js` already produces
exactly this event for first-party flows, and the registry already verifies
it (`domains/nostr.py verify_nip98`, URL binding, payload hash, single-use
`AuthEventSeen`). Nothing cryptographic is being invented — the missing
piece is a **mediated, origin-checked door** onto machinery that exists.

### Acceptance test

- Token for `https://pxls.hns.one/api/session` → accepted by the app server.
- Token for `https://hns.one/api/dns/mutate` → **refused by the mediator**.
- Token for `https://evil.example/…` → refused.
- The same token replayed → refused by the server (single-use).
- A token signed for name X presented as name Y → fails signature check.

## D2. `names.primary`

### The problem

The player brings "their main name". The standard has no way to ask which
that is. `names.list()` returns an array with **no ordering guarantee and
no flag**, yet the browser's own whoami pill plainly has an opinion and
IDENTITY.md onboarding produces one main name per user.

So an app must either guess `list[0]` — which signs people in **as the wrong
identity** — or prompt every single time, which is friction the browser is
already holding the answer to.

### The surface

Either is acceptable; the first is cleaner.

```ts
names: {
  primary(): Promise<{ name: string, tld: string } | null>
  // …or add to the existing list() entries:
  list(): Promise<Array<{ name, tld, granted: string[], primary?: boolean }>>
}
```

`null` is a legitimate answer (no name yet, or the user has not chosen one);
the app then falls back to the picker.

### Client behaviour to preserve

`.pxls` already implements the forward-compatible ladder, so shipping
`primary()` later requires no app change: try `primary()` → honour a
`primary` flag → use the sole name if there is exactly one → otherwise open
the mediator's picker. **Never guess `[0]`.** Worth writing into the spec as
guidance, because the naive implementation is the wrong one.

## D3. "A provider's name list is not an authentication result"

Nothing in §5 says an app's **server** must not trust what the provider
reports about identity. The naive app builds its leaderboard on
`names.list()` and is trivially spoofed by anyone who can talk to its API.

Add to §5.2, normative:

> A provider's responses are a **user-interface convenience, not an
> authentication result**. An app's server MUST independently verify any
> identity it acts on — for a Handshake name, against that name's own
> `_hns` control record, or by verifying a NIP-98 token per
> `identity.authenticate`. Apps MUST NOT treat `names.list()` or
> `names.request()` output as proof of control.

Cheap to add, and the whole point of the standard is that app authors should
not have to be security engineers to get this right. `.pxls` does verify —
but it had to work that out rather than read it.

---

## D4. `names.request({})` with no tld

§5.2 types `request(opts: { tld?: string })` — optional — but does not say
what the picker offers when it is omitted. An app with `any-held-name`
scope has no other way to say "any name you hold".

> An omitted `tld` means the picker offers every name in scope for the
> app's granted capabilities.

## D5. An app hosted on HNS cannot be used AT its Handshake name

Found 2026-08-24 by deploying `.pxls` to the `pxls` zone itself.

### The problem

§3 requires `ui.entry` to be a single origin, and §5.1 injects the provider
**only into frames whose origin exactly matches it**. `.pxls` declares
`https://pxls.hns.one/`.

The same application, byte for byte, is also served at **`https://pxls/`** —
the native Handshake name, which is the entire point of hosting an app on
Handshake. At that address it gets **no `window.handshake`**, so it cannot
sign anyone in, and it is not an installed app at all.

So: an app hosted on Handshake, reached at its Handshake name, cannot be a
Handshake App. The standard silently assumes apps live in DNS-land.

Two further consequences, both real:

* **Two origins, two states.** `pxls` and `pxls.hns.one` have separate
  `localStorage`, sessions and cookies — the same user is two users.
* **Auth cannot span them.** NIP-98 binds a signature to an exact URL, so a
  token minted for one origin is refused at the other (`url mismatch`).
  There is no way to declare "these two addresses are the same app".

### Proposal

Let `ui.entry` be a **list**, with the native name allowed to be one of them:

```json
"ui": { "entry": ["https://pxls/", "https://pxls.hns.one/"] }
```

Mediator rules:

1. Inject the provider into **any** listed origin.
2. Every listed origin MUST be provably the app's own name: either the
   Handshake name in `id`, or a gateway address for it. A manifest may not
   list an origin it cannot prove it owns — this is the check that keeps the
   list from becoming a way to borrow someone else's identity.
3. `auth.token`'s origin check (D1) widens to "any listed entry origin",
   never beyond.
4. Grants are keyed by app `id`, which is already a name — **not** by
   origin — so a user who granted at one address is granted at the other.

The app still has two browser origins and two `localStorage` jars; the
standard cannot fix that. But it can stop treating them as two apps, which
is the part that makes HNS-native hosting impossible today.

**Until this lands, an app must pick one address and tell users to use it.**
`.pxls` picks the gateway address, which is the reverse of what hosting on
Handshake is for.

## M. The mediator — already specified, not built

§11 already lists these. Restated as the subset `.pxls` actually needs, in
dependency order:

1. **Manifest fetch + validate + install.** Validate against
   `manifest.schema.json`; fail closed on unknown capabilities.
   (`pxls.app.json` validates today.)
2. **Grant store**, keyed by app id, per name, with revoke.
3. **Provider injection**, `window.handshake`, ONLY into frames whose origin
   matches `ui.entry`, `contextIsolation` on, from the main process.
4. **`version()`**, returning granted capabilities.
5. **`names.list` / `names.request`** (+ `primary`, D2).
6. **`auth.token`** (D1).
7. **Settings surface**: installed apps, grants, revoke.

Explicitly **not** needed for `.pxls` v1: `records.propose`,
`content.publish`, schema-template expansion, the consent overlay for
mutations, `dns.delegate`. `.pxls` declares `dns.set-record` for its
optional trophy record — **drop that capability from the manifest** if you
want the smallest possible mediator, and the app still ships whole.

### Unsigned manifests

`pxls` is held but not DNSSEC-anchored, so `signature.pubkey` cannot be
verified by a third-party host. Either answer §12 Q4 ("allow
install-with-warning?") or anchor the name first: sign the zone and commit
its DS on chain.

## R. Registry: accept an award voucher

Not a plugin change, but `.pxls` prize redemption does not work without it.

Winning entitles a player to a label the registry is configured to refuse
(`.pxls` runs `min_label_length = 4`; prizes are 1–2 characters). The app
mints a voucher signed by the `pxls` TLD's own control key:

```json
{ "v": "pxls-award-1", "tld": "pxls", "label": "q",
  "pubkey": "<64 hex>", "season_id": 1, "rank": 1,
  "expires_at": 1790000000 }
```

`web/domains/identity.py` `claim_identity` gains optional `voucher` +
`voucher_sig`, and when `len(label) < mn.min_label_length` the claim is
refused **unless** the voucher verifies: BIP-340 by the TLD's `_hns` control
key over the canonical JSON, `tld` matches, `pubkey` matches the claimant,
not expired, single-use.

The plugin side is then just `names.claim({ tld, label, voucher, voucher_sig })`
— a passthrough, no new consent shape.

## What ships at each stage

| Stage | Needs | `.pxls` is |
|---|---|---|
| **Today** | nothing | Runs standalone. Spectate from any browser; play only against a dev server. |
| **+ M1–M7 + D1** | mediator subset + auth verb | **Fully playable in Wildroot.** Gated sign-in with a real name, canvas, leaderboard, seasons, prizes awarded. |
| **+ D2** | primary name | Sign-in stops asking who you are every time. |
| **+ R** | registry voucher | Winners can actually claim their name. |

**D1 is the one that matters.** Everything else is polish or already
written down.
